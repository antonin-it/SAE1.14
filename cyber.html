De la requête au serveur

Anatomie d'un échange chiffré

Lorsqu'un utilisateur saisit une adresse dans son navigateur, plusieurs protocoles coopèrent pour localiser le serveur distant, authentifier son identité et établire un tunnel de communication chiffré avant même le transfert du premier octet HTML.

Étape 1

Résolution DNS

Le navigateur interroge un résolveur DNS pour traduire le nom de domaine lisible par l'humain en adresse I¨routable.L'extension DNSSEC ajoute une signature cryptographique à ces enregistrements afin d'empêcher toute falsification de la réponse (DNS spoofing).

Étape 2

Connexion TCP

Une fois l'afresse IP obtenue, le client et le serveur établissent une connexion fiable via la poignée de main en trois temps (3-ways handshake, SYN, SYN-ACK, ACK), garantissant que les paquets arriveront dans l'ordre et sans perte.

Étape 3

Negociation TLS (HTTPS)

Le serveur présente son certificat numérique signé par une autorité de confiance. Le client vérifie son authenticité, puis les deux parties utilisent la cryptographie asymétrique pour s'accorder sur une clé de session éphémère.

Étape 4

Échange HTTP chiffré

Le tunnel sécurisé est actif. Toutes les requêtes HTTP et les réponses du serveur (pages HTML, feuilles CSS, données de formulaire) circulent désormais chiffrées via un algorithme symétrique rapide, illisibles pour un intercepteur sur le réseau.

Côté code

Comprendre et bloquer les failles

Un transport chiffré en HTTPS protège les données en transit, mais ne corrige pas un code vulnérable. La majorité des compromission web exploite des entrées utilisateur mal contrôlées côté client ou côté serveur.

Injection SQL (SQLi)

Le mécanisme

Lorsqu'une application concatène directement la saisie d'un formulaire dans une requête de base de données sans filtrage, un ataquant peut modifier la structure même de la requête pour contourner une authentification ou extrairre des tables entières.

La parade

Utiliser systhématiquement des requêtes préparées (Prepared Statements) qui séparent strictement les instructions SQL des données fournies par l'utilisateur, et appliquer le principe du moindre privilège sur le compte SQL de l"application.

Cross-Site Scripting (XSS)

Le mécanisme

Une faille XSS survient lorsqu'un site réaffiche des données saisies par un utilisateur (commentaire, profil, paramètre d'URL) sans le neutraliser. Un acteur malveillant peut alors injecter du code Javascript qui s'exécutera directement dans le navigateur des autres visiteurs.

La parade

Échapper systématiquement tout les charactères spéciaux HTML avant affichage et déployer un en-tête HTTP Content-Security-Policy (CSP) pour restreindre l'origine des scripts autorisés à s'exécuter.

Mauvaise configuration des en-têtes HTTP

Le mécanisme

Par défaut, un serveur web peut laisser passer des requêtes non sécurisées, autoriser l'intégration du site dans une iframe externe (Clickjacking) ou exposer des cookies de session accessibles via JavaScript.

La parade

Forcer l'usage exclusif du HTTPS avec HSTS, isoler les cookies sensibles via les attributs HttpOnly, Secure et SameSite, et bloquer l'embarquement non autorizé avec X-Frame-Options.

Exemple d'en-têtes de sécurité HTTP recommandés (configuration serveur)

texte (En-Tête HTTP)

Strict-Transport-Security: max-age=31536000; includeSubDomains
Content-Security-Policy: default-src 'self'; img-src 'self' data:;
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin

Côté infrastructure

Durcire le serveur d'hébérgement

Une fois le code sécurisé, il faut réduire au minimum la surface d'attaque du système d'exploitation qui l'héberge. Le durcissement (hardening) d'un serveur Linux repose sur une défense en profondeur, si une couche cède, les suivantes bloquent la progression.

Exposition réseau & Tubbels chiffrés

Plûtot que d'ouvrir directement les ports d'adrministration sur Internet, l'exposition des services passe par un tunnel chiffré ou un pare-feu restrictif appliquant une politique de blocage par défaut (Deny by default). Seuls les flux web légitimes (HTTP/HTTPS) atteignent la machine.

Accès d'administration SSH verrouillé

L'authentification par mot de passe est totalement désactivé au profit d'une paire de clé cryptographique asymétriques (ed25519). La connexion directe avec le compte root est interdite, obligeant chaque administrateur à passer par un utilisateur nominatif et une élévation de privilèges journalisée (sudo).

Cloisonnement des sevices et permissions

Les applications web tournent sous des utilisateurs système dédiès sans shell interactif, avec des droits de lecture/écriture strictement limités aux répertoires nécessaires. L'utilisation de conteneurs isolés permet également de séparer chaque brique logicielle du système hÔte.

Mises à jour et supervision

L'application régulière des correctifs de sécurité du noyau et des paquets systèmes, couplée à l'analyse des journeux d'événement (logs) et au blocage automatique des tentatives d'intrusion répétées, assure le maintien en conditions de sécurité dans la durée.
